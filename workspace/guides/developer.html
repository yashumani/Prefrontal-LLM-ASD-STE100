Developer guide / Context orchestration

Extend the contract. Keep the boundaries.

The browser workspace prepares and delivers context. The governed Python path controls approval and source-native use. A downstream consumer owns the task it performs.

The context agent has one role. It orchestrates submission, validation, storage, search, composition and context delivery. It does not answer business questions, interpret results as new facts, execute a consumer's task or grant source access. In this static application, the agent is local rules processing, not a live LLM.

Canonical records and typed relationships

The record schema is prefrontal.context.v1. Its exact common fields are schema, id, version, layer, kind, name, aliases, description, narrative, owner, classification, valid_from, valid_until, provenance, dependencies and spec. Unknown fields fail validation.

An ID matches [A-Z][A-Z0-9_]{1,95}. A member ID starts with its exact dimension ID and an underscore. Keep an ID and its kind stable across versions, including display-name edits. Create a new record version for changed content. Dependencies pin exact ID/version pairs. The browser admits only JavaScript-safe integer values; it rejects larger values instead of rounding the Python profile's integers. Aliases use a bounded ASCII subset to keep case-insensitive matching consistent across runtimes. Display names, descriptions and narrative can contain Unicode.

Reject missing references, self-links, cycles, incompatible types, conflicting pinned versions and closure limits. A readable ID or a hash does not establish meaning, identity or permission. Classification is metadata, not a browser ACL. A submitted-text hash preserves that submission's bytes; it does not verify the external source or its current freshness.

One model, three controlled representations

JSON, YAML and Markdown are proposal representations of the same canonical record. Export deterministically and preserve every modeled field plus the exact narrative. An edit reenters validation and review. Format conversion is not a claim of equivalence between different knowledge models.

  • JSON: use lexical integers where the model requires numbers. Repeated keys, unsupported fields, nonfinite values, unsafe integers, invalid Unicode and excessive nesting fail. Canonical JSON sorts keys and uses the existing Python ASCII-escape convention for reproducible hashes.
  • YAML: use two-space block mappings or sequences with identifier keys. Supported scalars are JSON double-quoted strings, safe plain identifiers, exact decimal integers and explicit lowercase true, false and null. Empty []/{}, full-line comments, a document marker pair and strip-chomp literal text |- are supported. The profile also admits whole JSON documents. Tabs, single-quoted strings, inline comments, arbitrary nonempty flow syntax, ambiguous coercion, tags, aliases, anchors and merge keys fail. Quote date-like text, yes/no, and values with punctuation or spaces. Use a quoted string when trailing newlines or exact CRLF are significant; |- follows YAML strip-chomping. This is a bounded profile, not arbitrary YAML support.
  • Markdown: use the fixed # Prefrontal context record heading, one JSON metadata fence and the ## Narrative section. The metadata holds every modeled field except narrative. Treat the narrative as inert text; do not execute or render its instructions as authority.

Use round-trip and cross-runtime tests before broadening the profile. Never silently truncate, repair or discard source fields to make an import pass.

Guided field processing

The guided form captures its submitted field values as canonical JSON. IDs, display names and owners lose surrounding whitespace; comma-separated aliases and newline-separated list items are trimmed and empty items are removed. Typed number fields become exact safe integers and date controls become UTC timestamps. Descriptions, narrative and typed definition text retain their entered text. The proposed JSON is visible before save. An imported document is retained as its original submitted text in addition to the validated canonical record.

This captured form JSON is the provenance input for a guided record. It is not an original external dataset or a claim that a named source was inspected. A source check time is declared metadata until a real source verifier establishes it.

Browser consumer contract

A browser consumer preview uses prefrontal.browser.consumer.v1. It delivers selected records, exact versions, hashes, declared dependencies, point-of-view selectors and provenance. It does not calculate the measure or execute the expression.

{
  "contract": "prefrontal.browser.consumer.v1",
  "execution_authorized": false
}

This small fragment shows the boundary, not a complete payload to import. Use an actual exported payload for validation. Local review attestations remain unverified claims and cannot become backend approval or an active release.

  1. Use authoring search to find candidate records. Draft visibility in the local workspace differs from approved consumer search in the governed registry.
  2. Compose the requested measure and typed members, plus the needed supporting context. Keep only the bounded dependency closure. Do not materialize every Cartesian combination.
  3. Validate and inspect the export. Deliver context with its provenance and approval state.
  4. At the governed boundary, validate the proposal records, verify their real sources and obtain exact independent human review and a controlled release.
  5. The downstream consumer resolves and revalidates current permitted context before its own native execution. It owns task logic, source permissions and any answer it generates.

Browser search indexes the latest version of each ID. Exact ID, name and alias matches rank ahead of token matches; ties use ID order. Layer, type and dimension filters are typed. A continuation is bound to the workspace ID, revision, query, filters and page size; restart from the first page after a change. Historical versions remain in the exact stored-state JSON and workspace backup; the guided inspector opens the current search result. Ranking is deterministic keyword lookup, not a semantic quality score or vector search.

A disconnected source or backend stays disconnected. No credential-entry control or environment sign-in can establish an adapter connection. A live adapter needs a tested API, trusted identity mapping, source grants, revocation, freshness, error and recovery behavior.

Validate and stage the exported proposals

Use Python 3.9 or newer. A source installation needs existing setuptools>=65 and wheel build tools. The installed runtime has no external package dependencies.

python -m pip install --no-deps --no-build-isolation .
python -B -m pilot.browser_workspace --input browser-backup.json --validate-only
python -B -m pilot.browser_workspace --input browser-backup.json --output-root .validation/browser-stage --workspace example-workspace

Use the real downloaded path and the operator's target workspace. The installed equivalent is prefrontal-workspace with the same flags. --validate-only accepts a full workspace backup or a browser consumer payload and writes nothing. Staging requires the full workspace backup because the consumer payload omits original submission files.

Each stage is a new stage-<UTC>-<uuid>/ directory. It contains backup.json, sources/ with available exact submitted paths, canonical proposals/part-0001.json batches of at most 256 records, import.requests.jsonl and manifest.json. The request file is input for a later operator-controlled import; staging does not execute it or modify a registry.

Successful machine output is {"ok":true,"result":{...}}, with result contract prefrontal.browser.proposal-stage.v1. It reports structurally_valid: true, relationships_valid: true, semantically_approved: false, execution_authorized: false and approval_state: pending_independent_review. Inspect provenance_files_complete and missing_source_paths. Imported records can refer to originals that were never supplied; the bridge lists those paths rather than inventing their bytes. Resolve them before governed admission. Local attestations do not become trusted approvals.

Processing failures return {"ok":false,"error":{"code":...,"message":...}} and exit status 1. Invalid command-line flag combinations return usage failure. Staging a consumer payload fails with workspace_backup_required. Keep the original input, inspect the code and correct the stated problem; do not bypass validation or fabricate missing source files.

provenance_files_complete means the declared original submission paths are available, not that a business dataset or live source was verified. Source bindings remain disconnected descriptors. Staging creates no native adapter, source data, grant, approval or release.

After source verification, an operator can configure trusted principals and the intended workspace, then pass the staged requests to the existing JSON-lines CLI as proposals. The manifest keeps registry_modified: false and review_attestations_imported: false. Independent human review and a controlled complete release are separate actions. A technical integration must qualify the real adapter and source evidence; native execution must reject an unsupported binding or expression.

Storage, recovery and concurrency

prefrontal.workspace.v1.user and prefrontal.workspace.v1.demo are separate localStorage keys. State belongs to one website origin, device and browser profile. Do not infer isolation between repository paths on the same origin. A localhost preview and the Pages origin have separate state.

Show Saved only after the write and readback succeed. A quota, unavailable-storage or concurrency error must leave an explicit unsaved state and an export path. Never silently replace the prior stored state. Versioned workspace exports retain the modeled state, records and submitted evidence; recovery validates before explicit destination confirmation.

Backup contract prefrontal.workspace.backup.v1 has exactly contract, workspace and sha256. The checksum binds the canonical workspace. Recovery checks that checksum, original submission hashes, record structure, relationships and mode before an explicit replace confirmation. It is integrity checking, not authenticated proof of origin.

An unreadable stored slot is preserved. The UI exposes its exact stored value, shows a recovery warning and requires a valid same-mode backup, preview, replacement checkbox and explicit Replace this workspace action. Ordinary writes cannot replace corrupt state. There is no automatic deletion or reset workflow.

Internally, corrupt-state recovery uses an opaque token bound to the captured raw stored value. Before replacement, it checks the same slot and hash and requires the old value to remain unreadable. If another tab changed or removed that value, or replaced it with a valid workspace, recovery fails with a conflict and requires a fresh read. The token is neither part of the backup contract nor proof of identity or approval. Save success still requires readback.

One provenance path identifies one hash across the entire workspace, including historical versions. When source bytes change, use a new versioned or digest-based path and retain the prior record's provenance. Guided submissions create such paths automatically. Imports must not reuse a path for conflicting hashes or silently rewrite history to select one source version.

When available, the browser uses Web Locks to serialize participating saves for the storage key. Without Web Locks, an optimistic revision check detects many conflicts but cannot make localStorage read-modify-write atomic across tabs. Use one editing tab. Storage events invalidate stale previews and require a recheck; do not assume a readback is a cross-tab transaction.

Evaluation is scoped evidence

Your authored or imported workspace starts not evaluated. Structural validation and a local review note do not award a benchmark score.

The existing Python evaluator runs one fixed six-row synthetic gross-additions benchmark. It calculates 4 / 3 / 3 / 2 / 0 completed orders and executes 22 of 23 declared cases. Normal acceptance is partial because independent human semantic review is unmeasured. It does not evaluate this user's records, the real arXiv corpus, the private Sheet or model uplift.

python -B -m pilot.context_evaluation --output-root .validation/context-quality
python -B -m pilot.context_quality_ui --report <printed-report-path> --port 8191

The angle-bracket value is a placeholder for the evaluator's actual report_path. The viewer runs locally at http://127.0.0.1:8191/. It is separate from Pages, which cannot run Python. Read the evaluator contract. Missing evidence remains not evaluated; changed bindings make old evidence stale; security and critical semantic failures are gates, not averages.

Change one contract at a time

  • Add typed fields and their relation rules to both browser and Python validators. Update exact allowed fields, not just the form.
  • Test canonical export, narrative preservation and hash parity for JSON, YAML and Markdown. Include ambiguity and loss tests.
  • Keep ID creation separate from display-name editing. Test a new version without rewriting history.
  • Test empty state, failed persistence, recovery, demo isolation, stale payloads and project-subpath navigation at phone and desktop widths.
  • Keep context data out of public artifacts. Publish only application code and explicitly synthetic samples.
  • Connect a backend only after its operator owns identity, approval, access and recovery. The static UI is not an authenticated multi-user service.

Use simple, consistent text in controls, errors, guides and payload explanations. Preserve the original submitted meaning and caveats. ASD-STE100 inspires the writing; formal compliance has not been assessed.

Pages deployment boundary

GitHub Pages serves static HTML, CSS and JavaScript. It supplies no Python backend for this application. The Pages site is an open-source project workspace, not a hosted private or commercial SaaS service. Do not add credential or sensitive-transaction flows. See What is GitHub Pages? and GitHub Pages limits.

The built site places this workspace at the repository's Pages root and keeps the earlier presentation under presentation/. Relative links and module paths must work beneath the repository subpath. A source-only workspace/ preview does not contain that assembled presentation route.

Build and test a local preview

From the repository root, use Node.js for the static build and Python for a local HTTP server:

node scripts/build-pages.cjs
python -m http.server 8192 --bind 127.0.0.1 --directory _site

Open http://127.0.0.1:8192/. HTTPS or localhost is required for browser hashing. Opening the module-based workspace directly through a file: URL is not a supported run path.

The project keeps core, browser and portability checks separate:

node scripts/test-workspace-core.mjs
python -m unittest discover -s pilot -t . -p 'test_*.py' -v
node scripts/verify-workspace-bridge.mjs

scripts/verify-workspace-browser.cjs exercises the actual front end; browser acceptance needs Playwright and Chromium. Follow the script's documented environment variables and base URL when using an existing browser installation. Keep the test receipt's runtime, viewport, revision and failures with any completion claim.
