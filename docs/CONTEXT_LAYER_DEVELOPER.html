Developer journey / the supported path

Submit a version.
Review its exact meaning.

Prepare source and scope

Supply copied synthetic fixtures; identify order grain, USD cents, September period, population and evidence bytes. Keep source certification distinct from hash checking.

Construct four linked records

records(registry, now) prepares the data, metric, ontology and interpretation fixtures. Evidence uses relative paths plus SHA-256. Dependencies pin exact versions.

Submit and retain the receipt

Registry.submit(actor, body) returns a full-record hash. IDs remain stable; new versions are sequential. Same-version changed content fails immutable_version.

Review, reject or request changes

Use approve(..., expected_hash) or hold_review(..., decision). There is no reject() or request_changes() method. Held versions require a new version, not an in-place unhold.

Publish the complete manifest

publish validates all four layers, exact dependencies and source bindings, then commits release, derived index, active pointer and events together. Approval alone does not change the active release.

Retrieve context; execute natively

Only context.get and context.search are exposed by the JSON-lines CLI. Mutation APIs are Python methods. Native SQL and source permissions stay in NativeSales.

Return feedback through review

feedback records a pending-review event. Changed evidence/meaning needs affected-record versions, review and publication. Feedback never edits approved meaning automatically.

Simulation boundary

domain-owner, reviewer and release-owner are test configuration. The example checks roles and self-approval locally; it neither logs in a person nor proves real human review.

Data contract / complete record, complete meaning

The record is the unit of review.

Top-level keys must be exactly the set below. Extra top-level keys fail validation; required layer fields are a subset of content, where extra keys may exist without acquiring semantic validation.

id · version · workspace · layer · owner · claim · classification · valid_from · valid_until · evidence · dependencies · content
  • id: [a-z][a-z0-9_.:-]{1,100}. version: integer ≥ 1; no booleans.
  • layer: data, metric, ontology or interpretation. classification: internal or restricted.
  • Timezone-aware ISO validity timestamps; start must precede end. The fixture interval is 30 days from run creation, not a business refresh SLA.
  • Nonempty evidence: exact {path, sha256} objects. SHA-256 is lowercase 64-hex. Paths stay under the source root.
  • dependencies: exact {id, version} objects, no duplicate pairs. Every non-data record needs a dependency.

What a future BI comparison needs

There is no prior-month data, date dimension, customer/product/region join or natural-language parser here. Add reviewed prior-period sources, compatible populations, calendar/timezone/partial-month rules, cardinality/grain checks, currency/returns policy and zero/missing-denominator handling before calculating month-over-month change. Revenue alone establishes neither profit nor the cause of a change.

A question / process / evidence three-panel product UI is a proposed design. This presentation is an educational map and captured replay, not that operational interface.

Expiry or revocation does not eagerly purge the index. Current canonical checks deny invalid referenced content, including cached native use. The whole release is checked; the pilot does not return a filtered partial release.

Policy still needed

Reviewing every dependent record after every row refresh may be expensive. Distinguish owner-approved source/schema/definition changes from routine refresh admitted under an explicit freshness/validation policy. Measure hands-on minutes, blocked tasks and interventions before estimating staffing, recurring cost or business return.

Failure contract / controlled outcomes

Explain the denial.
Repair the cause.

Dispatch failures return only {"ok":false,"error":"code"}, with no record/evidence payload. Source-service failures are separate Python exceptions. Do not bypass a denied grant or “repair” integrity by trusting a client bundle.
